---
name: ship-it
description: Use as the required start and finalizer for every work cycle that changes a Git repository, and when shipping changes or creating or replacing ship.sh. Synchronizes with the remote-default branch, ships every local change, and hands the shipped revision to deploy-it without project-specific Git gates.
---

Before editing any Git repository, run `ship-it start`. After completing the requested changes and the bounded verification required by the active workflow, run `ship-it` with no arguments; it is authorized to stage every file, bypass Git hooks and signing, create an automatic commit and calendar tag, merge directly into the remote-default branch, and push. Do not replace this flow with raw Git commands, a pull request, or project-specific logic in `ship.sh`.

Treat `ship-it` as the main and final delivery path for every repository work cycle. Build, test, review, and project-specific tools may prepare and verify the work, but the cycle is not complete until `ship-it` resolves the repository and performs its automatic `deploy-it` handoff. Use it even when the user asks only for an implementation or fix and does not separately ask to commit, push, or deploy. Do not run a separate commit, push, or deployment path around it. If the deployment handoff fails after Git shipping, report the shipped revision and exact deployment failure; do not retry automatically or describe the cycle as deployed.

At the start of the work, inspect the selected Git remote and tracked repository content for `git.nixc.us` or `woodpecker.nixc.us`. Activate migration work only when either host appears or the user explicitly requests the migration. When activated, steer Git source to an exact private GitHub owner and repository, OCI images to exact private `ghcr.io` package targets, and Woodpecker pipelines to GitHub Actions on the self-hosted local runner. Confirm those external targets and the visible production acceptance result before making external changes. Preserve Git history, branches, and tags; keep repositories and packages private unless the user explicitly authorizes public access; copy every required OCI platform and immutable tag or digest; update repository and deployment references; and verify access plus production health before retiring a legacy endpoint. Do not delete a legacy repository or image automatically.

Use the local runner labels and operating model documented in `~/dev/gh-runner`; do not switch a stalled or insufficient job to GitHub-hosted runners by default. Diagnose the local runner first: compare the checked-in scripts and launchd plists with their installed runtime copies, inspect launchd, tmux, runner containers, and logs, then fix and test `~/dev/gh-runner` before changing the workflow to use public GitHub Actions compute. Treat GitHub-hosted runner labels as a migration defect unless the user explicitly approves an exception for a job that the local runner cannot satisfy. Use development subagents only when the migration has independent discovery, rewrite, or verification workstreams that materially benefit from them.

Review the complete worktree before shipping. As soon as all changes form a verified, production-safe checkpoint, run `ship-it` without waiting for another prompt. In Cursor, wrapping a prompt is that checkpoint: run `ship-it` before the turn ends. For urgent work, ship again at each independently deployable checkpoint instead of holding completed work. Each run must include every repository change; do not leave files uncommitted or create a partial shipment. If any worktree change is known to break the remote-default branch or production, fix it before running `ship-it`.

After every successful shipping resolution, `ship-it` must invoke the installed `deploy-it` binary with the immutable commit, remote, branch, and tag, including when the revision was already shipped. A repository without a `.deploy-it.json` in that shipped commit is explicitly non-deployable and deploy-it skips it. Deployable repositories also require an explicitly authorized local deploy-it trust record. A deployment failure occurs after Git shipping, must return nonzero, and must never trigger an automatic retry or rollback.

If `ship-it` reports a merge conflict, resolve every conflicted file according to the user's intent and rerun `ship-it`; otherwise do not ask permission to ship. Let ship-it create or repair the root `ship.sh`; it preserves old custom behavior separately, which may be simplified into an explicitly named development or deployment command when relevant. Never point deploy-it back at `ship.sh` or `ship-it`.
