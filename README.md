# ship-it

`ship-it` is one no-argument command for routine Git delivery.

Before the first delivery each local day, it runs `git pull --autostash`. Every bare invocation then runs `git add .`, creates an automatic commit when changes are staged, and runs `git push` in the same call. Scripts and agents do not select a lifecycle phase.

Shipping stages all changes without content selection or approval prompts. Neither shipping nor deployment requires a clean worktree. Deployment runs from a private snapshot of the exact pushed commit, so local worktree and index changes do not block it or enter the snapshot.

Native Codex and Cursor lifecycle hooks invoke the same binary. Session start ensures the daily pull has happened. Stop ships the completed coding cycle. After a successful push, a tracked `.deploy-it.json` triggers `deploy-it` for the repository’s declared destination. Repositories without a deployment contract still ship normally. Repositories with no configured Git remotes skip delivery, leave local work untouched, and report the skip in the hook message and diagnostic log. They remain eligible for delivery after a remote is configured. Errors from configured remotes still fail delivery. Git delivery requires no verification contract, tags, branch switches, wrapper scripts, or GitHub Actions policy.

When a hook selects several repositories, it attempts every publication before starting any `deploy-it` handoff. Each handoff keeps the exact pushed commit and destination. The detached ship-it worker uses `deploy-it --wait` to observe the durable deployment operation through its final command result. Enqueue success alone never counts as completed delivery. Publication and deployment acquire the same repository lock separately; deployment rejects a captured revision if a newer push has replaced it. A failed publication or deployment does not stop later repositories. Git webhooks can still start Jenkins as soon as each push arrives, before the remaining pushes finish.

Run `ship-it install` once to install the binary, skill, and lifecycle hooks. Routine use requires no arguments or agent involvement.

Codex command hooks use `async: true`. Native Codex and Cursor lifecycle calls queue a worker in a separate process session and return valid JSON with its log path immediately. The worker keeps file-backed input and output, so cancellation of the hook runner does not cancel delivery. Each private log under `~/.local/share/ship-it/hooks/` records the worker PID, command output, and eventual completion or failure. A queued message confirms the handoff only. Delivery feedback is advisory and cannot request another agent turn. The 300-second Codex hook timeout bounds the launcher, not the detached deployment observer.

`ship-it install` also registers the installed `one-shot-tally` binary for Codex `PreToolUse` and `PostToolUse`. When it observes an explicit native edit in another repository, Stop also includes that repository. Read-only access does not select a repository. Pending delivery survives a failed deployment even when Git is clean. If another Stop arrives during an existing continuation, one retry is allowed for an unchanged failed edit. Delivery never creates that continuation. A new turn or changed working files can retry again, even if an edit observer misses the change. Failed attempts retain the file snapshot taken before delivery, including repositories named directly in the hook. Older attempts without a snapshot get one retry. A successful delivery clears only its captured edit generation and exact clean revision. SessionStart keeps its original repository scope.

The registry uses the native session ID. Historical edits made before installation, opaque shell edits outside the known roots, and child sessions with a different ID are not inferred. A kernel file lock protects registry updates; it does not claim to deduplicate concurrent initial Stop events.

Existing tabs can retain the old `ship-it hook` or `ship-it cursor-hook` handler with a five-second timeout. These handlers use the same detached worker as the installed no-argument hooks. To check a background delivery, read the returned log and its final `completed` or `failed` record. If it fails, use the recorded command error and deployment handle to recover the existing operation; a queued record alone does not prove a push or deployment.

The tracked deployment contract submits the exact pushed `main` revision to the existing Jenkins `deploy-ship-it` job at `http://127.0.0.1:16155`. Jenkins builds, tests, publishes an immutable artifact, installs `/Users/aedev/.local/bin/ship-it`, and verifies the installed binary. The repository command only submits or observes that operation; it does not install a local build.
